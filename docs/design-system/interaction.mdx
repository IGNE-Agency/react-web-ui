# Interaction

A screen can't give way under your finger, so a control has to answer some other way. It lights up when you point at it, gives when you press it, shows where the keyboard is, and tells you before you click what the click will do. When those answers are right, nobody thinks about the interface. When they're missing, every control becomes a small gamble.

<Illustration caption="Pointer, keyboard, voice, touch, pen or switch: six ways in, and one control that reaches into every one of them.">
	<InteractionDrawing />
</Illustration>

## Every control answers back

People reach a control in three ways: with a pointer, with a finger and with the keyboard. Each asks something different. The pointer asks whether this can be clicked, and the control answers by brightening a little when the pointer arrives and a little more while it's pressed. The keyboard asks where it is, and the answer is a ring around whatever it has reached. A finger gets no hover at all, so the press itself has to be enough.

The answers only work if they're the same everywhere. A reader learns them once, on the first screen, and trusts them on every screen after. A control that answers differently, or not at all, looks broken even when it works.

Here, every control answers the pointer with [the shared state layer](?path=/docs/design-system-foundation-states--docs#the-state-layer), a thin wash of its own ink, and the keyboard with [one focus ring](?path=/docs/design-system-foundation-states--docs#the-focus-ring), drawn the same way on everything.

## Where the keyboard is

For someone on the keyboard, focus is the cursor. Lose sight of it and they're lost on the page, with no way of knowing what the next key will press. So anything you can click, you can also reach with the keyboard, and wherever the keyboard lands, the ring is there. Leaving it off doesn't bring back the browser's own outline: this product removes that everywhere, so a control without the ring shows no focus at all.

Focus is two states, not one. <Pull>A field's border warms whenever focus is anywhere inside it, however it arrived; the ring is keyboard focus and only keyboard focus.</Pull> Merge the two and a mouse click draws a keyboard ring, or a field you clicked into looks untouched.

## Promises before the click

Before anyone clicks, the screen has already told them what the click will do. The cursor changes shape over something that acts, a line under a word says it leads somewhere, and a different line says it opens something here. These are promises, and the interface keeps them only if they're made the same way every time.

<Illustration caption="Two words marked in a line of text. A solid underline promises the click goes somewhere else; a dotted one promises it opens something right here.">
	<PromisesDrawing />
</Illustration>

The cursor comes in four shapes, each a promise about the click:

- **Pointer** over anything that acts on a click: buttons, links, the summary of a fold, and the controls that aren't text entry, like selects, checkboxes, radios and switches.
- **Not allowed** over anything disabled.
- **Text** over text entry. A text field, a text area and the message composer don't take the pointer: a click there puts a caret where you clicked, and the I-beam says so.
- **Arrow** over a control that can only be read. Text entry keeps its caret even then, because its text can still be selected.

A label isn't in that list. It's the field with a larger target, not a separate thing to click, so it takes the cursor of whatever it labels: the arrow over a text field's label, the pointer over the label beside a checkbox, a radio or a switch, where the whole row is one target.

## Names for silent controls

<Pull>
	An icon with no text is unlabelled to a screen reader and
	a guess to everyone else.
</Pull>
So a control that shows only an icon always carries two
things with the same words: a name that assistive technology
reads out, and a tooltip that shows on hover and focus. That
goes for menu triggers, close buttons, paging arrows, a
chip's remove button and toolbar actions alike, and [the
icon-only
button](?path=/docs/components-button--docs#an-icon-only-button-is-a-circle-with-an-accessible-label)
gives both for free.

The browser's own hint, the `title` attribute, does neither job. Screen readers treat it unreliably, it never shows on touch, it can't be styled or themed, and the keyboard can't reach it. Whatever it was carrying belongs in [a name the control points at](?path=/docs/design-system-principles-accessibility--docs#every-control-has-a-name-from-exactly-one-mechanism) and in the tooltip.

<DoDont>

## Technical rules

Every rule on this page, one sentence each, for looking up rather than reading. Open one for the details and the code.

<DetailsList>

<Details title="Hover and press come from the shared state layer">

The layer paints a translucent wash of the element's own content colour over its fill, so one recipe covers every variant. How strong it is for each state, in each theme, is on [States](?path=/docs/design-system-foundation-states--docs#the-state-layer). Explained in [Every control answers back](#every-control-answers-back).

<DoDont>
<Example kind="do" caption="One translucent layer of the item's own ink covers every variant.">

```scss
.nav-item {
	border-radius: var(--radius-full);

	@include state.layer;
}
```

</Example>
<Example kind="dont" caption="A hand-picked hover colour per variant, none of which themes.">

```scss
.nav-item {
	&:hover {
		background: #f2f2f2;
	}
}
```

</Example>
</DoDont>

</Details>

<Details title="A row or tab that should read as picked out swaps its fill instead of taking the layer">

Table rows and tabs hover to a tint, so they read as picked out rather than dimmed. Shown in [Every control answers back](#every-control-answers-back).

<DoDont>
<Example kind="do" caption="The hovered row steps to a tint of the brand.">

```scss
.row:hover {
	background: var(--row-hover);
}
```

</Example>
<Example kind="dont" caption="A layer of the row's own ink only greys it.">

```scss
.row {
	@include state.layer;
}
```

</Example>
</DoDont>

</Details>

<Details title="Everything you can reach with the keyboard shows the focus ring">

Every focusable element includes the shared ring; the reset has already removed the browser's outline, so a hand-rolled ring drifts and a missing one hides focus. Use the idle and shown variants to drive one element's ring from another element's focus. Explained in [Where the keyboard is](#where-the-keyboard-is).

<DoDont>
<Example kind="do" caption="Every focusable element draws the one shared ring.">

```scss
.my-button {
	@include focus.ring;
}
```

</Example>
<Example kind="dont" caption="A hand-rolled ring drifts in colour, width and offset; removing the outline just hides focus.">

```scss
.my-button {
	&:focus-visible {
		outline: 2px solid var(--sys-color-primary);
		outline-offset: 2px;
	}
}

.my-button {
	outline: none;
}
```

</Example>
</DoDont>

</Details>

<Details title="A field's border warms on any focus, and the ring is keyboard focus only">

A form control publishes both states, like every other state: `[data-focused]` and `[data-focus-visible]`, from `useFieldFocus`. It does not read `:focus-visible` or `:focus-within`, for the same reason it does not read `:disabled`: one vocabulary, so a rule written against a field reads the same wherever it is. It also covers focus that has moved into a portalled popup, which is nowhere near its trigger in the DOM, and lets a story stand the state up without focusing anything.

This covers wrappers as well as bare controls, which is why there is no within-variant of the ring: a wrapper whose focus lands on a descendant, like a field group or the composer around its contenteditable, publishes the same two flags from the same hook, because React's focus events bubble. A button, a link, a nav item or a tab has no state to publish and keeps `focus.ring` on `:focus-visible`. Shown in [Where the keyboard is](#where-the-keyboard-is).

<DoDont>
<Example kind="do" caption="The projection answers both questions.">

```scss
.group {
	@include focus.ring-projected;

	&[data-focused] {
		border-color: var(--sys-color-primary);
	}
}
```

</Example>
<Example kind="dont" caption="Two vocabularies in one stylesheet, and a mouse click rings the field.">

```scss
.group {
	&:focus-within {
		@include focus.ring-shown;

		border-color: var(--sys-color-primary);
	}
}
```

</Example>
</DoDont>

</Details>

<Details title="A list whose highlight follows mouse and keyboard takes no ring on top">

The library's highlight is already the keyboard's mark, so it is the only mark on the row. Shown in [Where the keyboard is](#where-the-keyboard-is).

<DoDont>
<Example kind="do" caption="The highlight is the only mark on the row.">

```scss
.item[data-highlighted] {
	background: var(--sys-color-primary-container);
}
```

</Example>
<Example kind="dont" caption="A ring on top of the highlight marks the same row twice.">

```scss
.item {
	@include focus.ring;

	&[data-highlighted] {
		background: var(--sys-color-primary-container);
	}
}
```

</Example>
</DoDont>

</Details>

<Details title="Inside a scroll container the focus ring is inset">

An outward ring is clipped by the container's edge. Shown in [Where the keyboard is](#where-the-keyboard-is).

```scss
.tab {
	@include focus.ring;

	outline-offset: calc(-1 * var(--focus-ring-width));
}
```

</Details>

<Details title="A non-focusable element is decoration, not an exemption">

A row that highlights on hover is decoration, and a wrapper label is not the focus target; the controls inside them are. If an element is clickable, it is focusable, and it needs both states. Shown in [Where the keyboard is](#where-the-keyboard-is).

<DoDont>
<Example kind="do" caption="The row's highlight is decoration; the link inside it is what a key reaches.">

```tsx
<tr className={styles.row}>
	<td>
		<Link to={href}>{name}</Link>
	</td>
</tr>
```

</Example>
<Example kind="dont" caption="The row answers a click but no key.">

```tsx
<tr className={styles.row} onClick={open}>
	<td>{name}</td>
</tr>
```

</Example>
</DoDont>

</Details>

<Details title="The cursor says what happens on click">

Pointer for anything that acts on a click, including the ARIA roles a library renders in place of native controls; not-allowed for anything disabled, by the native attribute, the ARIA attribute or a library's data attribute; text over text entry; default over a read-only control, except text entry, which keeps the caret. Explained in [Promises before the click](#promises-before-the-click).

<DoDont>
<Example kind="do" caption="Text entry takes the I-beam; a checkbox's label takes the pointer.">

```scss
input,
textarea,
[contenteditable="true"] {
	cursor: text;
}

.checkbox-label {
	cursor: pointer;
}
```

</Example>
<Example kind="dont" caption="A pointer everywhere promises a click from a label, a text field and a disabled button alike.">

```scss
.text-field-label,
.text-field,
.submit {
	cursor: pointer;
}
```

</Example>
</DoDont>

</Details>

<Details title="A label takes the cursor of the control it labels">

The arrow over a text field's label, the pointer over the label beside a checkbox, a radio or a switch. Those three set it on their own label element; the global rule does not. Explained in [Promises before the click](#promises-before-the-click).

</Details>

<Details title="The cursor is given back once, globally, outranking the reset">

The global reset throws the user agent's cursor away along with everything else. Give it back once, globally, not per component. Watch the specificity: a reset that re-applies `cursor: revert` on `a, button` is a type selector, so a zero-specificity default loses to it, and `revert` on a button lands on the user agent's arrow, so links keep working while every button quietly stops. Component overrides still win, because they name a class. Explained in [Promises before the click](#promises-before-the-click).

<DoDont>
<Example kind="do" caption="Once, globally, outranking the reset's own selector; the disabled rule follows it.">

```scss
button,
select,
[role="menuitem"] {
	cursor: pointer;
}

:disabled,
[aria-disabled="true"],
[data-disabled] {
	cursor: not-allowed;
}
```

</Example>
<Example kind="dont" caption="The twelfth copy of a rule that is already global.">

```scss
.sort-toggle {
	cursor: pointer;
}
```

</Example>
</DoDont>

<Example kind="caution" caption="The reset's “a, button” outranks a zero-specificity default, so every button shows an arrow while links still work.">

```scss
:where(button, select, [role="menuitem"]) {
	cursor: pointer;
}
```

</Example>

</Details>

<Details title="A link carries the brand colour and is underlined">

Declare it as a zero-specificity default so links that are not body copy override it by naming their class. On hover it moves to the tonal container's ink. Chrome such as nav items, a rail's logo and a tab strip opts out by saying what it is. Explained in [Promises before the click](#promises-before-the-click).

<DoDont>
<Example kind="do" caption="One default, overridable by any class. Chrome opts out by saying what it is.">

```scss
:where(a[href]) {
	color: var(--sys-color-primary);
	text-decoration: underline;

	&:hover {
		color: var(--sys-color-on-primary-container);
	}
}

.nav-item {
	color: var(--sys-color-text);
	text-decoration: none;
}
```

</Example>
<Example kind="dont" caption="A second link treatment, unthemed, with the affordance removed.">

```scss
.forgot-password {
	color: #006d97;
	text-decoration: none;
}
```

</Example>
</DoDont>

</Details>

<Details title="Progressive disclosure is underlined dotted, not styled as a link">

The trigger sets the line and the text draws it: faded at rest, full strength on hover and while the popup is open, in the text's own colour. In a group of chips that opens as one trigger, the line goes in each chip, and the trigger owns the states. Explained in [Promises before the click](#promises-before-the-click).

<DoDont>
<Example kind="do" caption="The trigger sets the line, the text draws it.">

```scss
.group {
	--disclosure-line: color-mix(
		in oklab,
		currentcolor 50%,
		transparent
	);

	&:hover,
	&[data-popup-open] {
		--disclosure-line: currentcolor;
	}

	> * {
		text-decoration: underline dotted var(--disclosure-line);
	}
}
```

</Example>
<Example kind="dont" caption="A line under the group, and a trigger styled as a link.">

```scss
.group::after {
	border-block-end: 1px dotted var(--sys-color-outline);
}

.trigger {
	color: var(--sys-color-primary);
	text-decoration: underline;
}
```

</Example>
</DoDont>

</Details>

<Details title="An icon-only control always has a tooltip and an accessible name">

An icon-only control is the button component's icon-only form, which requires a label and surfaces it as both; a library trigger that needs to be one renders through it. Where a component wraps a library trigger, the label is a required prop, so the type check enforces it. Explained in [Names for silent controls](#names-for-silent-controls).

<DoDont>

The accessible name goes through a label the control points at, and the hint through the tooltip component, both with the same string. A `title` used to rescue a truncated label is a layout bug: wrap the label instead. Explained in [Names for silent controls](#names-for-silent-controls).

</Tooltip>

<button title={label}>
	<Icon svg={MenuIcon} label="" />
