# Colour

Colour is the first thing anyone takes in on a screen, before a single word is read. It groups what belongs together and sets apart what doesn't, says what you can act on and what needs your attention, and sets the mood of the whole product. That speed is exactly why it needs rules: a colour that means two things means nothing.

<Illustration caption="A ramp is one hue in even steps of lightness, from the palest tint to the deepest shade.">
	<ColourDrawing />
</Illustration>

## What colour does

Every colour on a screen is doing something. A tint behind a row says it's selected. A red border says something went wrong. A green button says this is the thing to press. Because colour is read so fast, it's the strongest signal a screen has, and the easiest one to wear out: paint everything and nothing stands out any more.

Colour also never works alone. Some people see fewer colours than others, screens get washed out by sunlight, and printers turn everything grey. So whatever colour says, a word, an icon or a shape says it too.

## Hue, lightness and chroma

Any colour can be described by three things. Its **hue** is which colour it is: green, blue, orange. Its **lightness** is how close it sits to white or to black. Its **chroma** is how much colour it has, from grey to as vivid as the hue goes.

Change just one of them and you get the words designers use every day. Mix a colour with white and you get a **tint**, with black a **shade**, with grey a **tone**. Line up one hue from its lightest tint to its darkest shade and you have a **ramp**, and a palette is a handful of ramps.

<Illustration caption="A colour picked the way a designer picks it: a hue on the slider, then lightness down the grid and chroma across it.">
	<DialsDrawing />
</Illustration>

## A palette with meaning

A palette with meaning isn't a collection of nice colours. It hands each hue one job and keeps it there. One hue is the brand's accent. A few hues are kept for status: success, information, warning, error. Neutrals carry the surfaces and the text. When a hue takes a second job, both jobs get weaker.

The brand colour is the accent. A status colour is a status colour and nothing else: it belongs on status chips, badges and toasts. It is never the hover, focus or generic accent, which is the default a lot of applications fall into, and never [the colour of selected text](?path=/docs/design-system-principles-interaction--docs#selected-text-is-a-role-not-a-browser-default).

## Seeing lightness evenly

How light a colour looks depends on its hue. A yellow and a blue with the same "lightness" in HSL look nothing alike: the yellow glows and the blue goes nearly black. That's because HSL describes how a screen mixes its red, green and blue, not how your eye sees the result.

<Illustration caption="Squint and only lightness is left: hues set in HSL break into light and dark stripes, the same hues set in OKLCH into one even grey.">
	<PerceptualDrawing />
</Illustration>

A perceptual colour space like **OKLCH** is built the other way round, from how people see. Its lightness is perceived lightness, so two colours at the same lightness look equally light whatever their hue, and the steps of a ramp look evenly spaced. Its chroma and hue are the same dials described above, which makes it the natural space to design a palette in.

## Mixing colours

Mixing two colours means walking a path from one to the other, and the colour space decides which path. **OKLab** walks a straight line: the hue never takes a detour, though the middle can come out a little greyer. **OKLCH** walks round the hue circle, keeping the colour vivid on the way, which is lovely for a gradient between two hues.

That circle is also its catch. White, black and greys have no real hue, so the path's direction depends on whatever tiny hue a neutral happens to carry. Mix a green tint into white and it stays green by luck. Mix it into a dark grey that leans slightly blue and the result can swing halfway round the circle. Pick the space by what should stay put: for a tint mixed into a surface, that's the hue.

## Contrast, held in reserve

This product's palette is soft and close-toned on purpose. <Pull>Contrast is a signal, not a texture: it belongs to what the user can act on and to what needs their attention, and it is spent sparingly even there.</Pull> Anything passive (a skeleton, a placeholder, a caption, a status dot at rest) sits one quiet step off the surface it is drawn on: enough to be seen at a glance, and never climbing toward the ink.

## Surfaces

A screen is a stack of surfaces: the page itself, the cards that sit on it, the fills inside those cards, and the popups that float above everything. Each level gets a tier of its own, so you can tell at a glance what sits on what. This product has seven: a page canvas, a dimmest card, the default card, a nested fill, the deepest recess, an overlay for popups and tooltips, and a higher overlay for toasts.

A surface gets **more tinted as you nest** and **lighter as you rise**. In light mode those pull in opposite directions, which is the thing to get straight: a nested fill is _darker_ than the card it sits in, while a popup floating above that card is not. Write the tier you mean rather than reasoning from "higher number means lighter".

## Surfaces on surfaces

Each tier has an occupant. Reach for one by naming where the thing sits, never by how light you want it to look.

| Tier | What sits there |
| --- | --- |
| Canvas | The page — the routed `<main>`, which takes no fill at all |
| Default card | A sheet on the page |
| Nested fill | A fill within a sheet: an expanded row's sub-table |
| Deepest recess | A well within that |
| Overlay | Off the ladder — popups and tooltips, with toasts on the higher overlay above them |

Read down that column and it is the component tree. Every level is a surface on the one below it, so a component only has to know its own depth.

The page is the canvas, not a surface on it. It declares no fill of its own, so what a sheet is read against is the canvas directly, which makes the canvas the one tier that is a _field_ rather than an object.

The ladder is shorter than the tree, so the rule is not one tier per level — it is **never invent a tier.** A level that would repeat its parent's fill separates by something else: the space around it, its own header band, or a line in [one of the four cases that justify a line](?path=/docs/design-system-principles-separation--docs#the-four-cases-that-justify-a-line).

<Details title="The dark theme is two conditions, kept behind one mixin">

A theme is two conditions, not one. The stored preference pins a theme, and its default follows the operating system — so a dark document is either the attribute or a `prefers-color-scheme` match with no attribute contradicting it. Following the OS is the media query's job, never a script's: a resolved-once attribute freezes on whatever page the user happened to load, and only re-resolves where a component that reads the preference is mounted. Because the condition is a pair of selectors, it lives behind a mixin (`theme.dark-root` at the root, `theme.dark` inside a rule) so no file spells out half of it.

<Details title="The theme is resolved in the HTML shell, before the first paint">

Resolve the theme before first paint, in the HTML shell. A framework cannot do this: its effects run after the browser has painted, so a dark-mode user gets a white flash on every full page load, including the reload that switching locale performs. The stylesheet is no help either — it is a module the app pulls in, so it lands after the first paint too. That takes two things in the shell: an inline script that pins the stored preference on the root element, and an inline style that states the canvas colour and `color-scheme` for both themes. Set the canvas colour on the root element as well as the body so nothing paints white behind the page.

<DoDont>
<Example kind="do" caption="The shell pins the stored theme before the browser paints anything.">

```html
<script>
	const theme = localStorage.getItem("theme");

	if (theme) document.documentElement.dataset.theme = theme;
</script>
```

</Example>
<Example kind="dont" caption="An effect runs after the first paint, so a dark-mode user sees a white flash on every load.">

```tsx
useEffect(() => {
	document.documentElement.dataset.theme = theme;
}, [theme]);
```

</Example>
</DoDont>

</Details>

<Details title="The shell's raw canvas colour is guarded behind its token">

The shell is the one exception to [colour values living only in the tokens files](?path=/docs/design-system-foundation-token-architecture--docs#a-colour-value-appears-only-in-the-tokens-files): a raw colour may be written there, and only for the canvas. Guard it behind the token so it expires: `var(--sys-color-bg, <raw>)` uses the raw value only while the stylesheet is missing, and every later load of the token wins on its own.

<DoDont>
<Example kind="do" caption="The raw value paints only until the token arrives.">

```css
html {
	background-color: var(--sys-color-bg, #1f2329);
}
```

</Example>
<Example kind="dont" caption="Unguarded, the raw value is a second canvas colour that has to be kept in step by hand.">

```css
html {
	background-color: #1f2329;
}
```

</Example>
</DoDont>

</Details>

<Details title="Scrim opacity is the one theme selector a component may hold">

<Beside>

The one legitimate use of a theme selector inside a component file is a value that is not a role and differs per theme, such as scrim opacity:

<Example kind="do" caption="Scrim opacity is not a role, so the component states its dark value itself.">

```scss
.backdrop {
	--backdrop-opacity: 0.22;

	background-color: black;
	opacity: var(--backdrop-opacity);

	@include theme.dark {
		--backdrop-opacity: 0.4;
	}
}
```

</Example>

</Beside>

</Details>
