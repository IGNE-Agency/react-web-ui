# Colour

Colour is the first thing anyone takes in on a screen, before a single word is read. It groups what belongs together and sets apart what doesn't, says what you can act on and what needs your attention, and sets the mood of the whole product. That speed is exactly why it needs rules: a colour that means two things means nothing.

<Illustration caption="A ramp is one hue in even steps of lightness, from the palest tint to the deepest shade.">
	<ColourDrawing />
</Illustration>

## What colour does

Every colour on a screen is doing something. A tint behind a row says it's selected. A red border says something went wrong. A filled button says this is the thing to press. Because colour is read so fast, it's the strongest signal a screen has, and the easiest one to wear out: paint everything and nothing stands out any more.

Colour also never works alone. Some people see fewer colours than others, screens get washed out by sunlight, and printers turn everything grey. So whatever colour says, a word, an icon or a shape says it too.

## Hue, lightness and chroma

Any colour can be described by three things. Its **hue** is which colour it is: green, blue, orange. Its **lightness** is how close it sits to white or to black. Its **chroma** is how much colour it has, from grey to as vivid as the hue goes.

Change just one of them and you get the words designers use every day. Mix a colour with white and you get a **tint**, with black a **shade**, with grey a **tone**. Line up one hue from its lightest tint to its darkest shade and you have a **ramp**, and a palette is a handful of ramps.

<Illustration caption="A colour picked the way a designer picks it: a hue on the slider, then lightness down the grid and chroma across it.">
	<DialsDrawing />
</Illustration>

## A palette with meaning

A palette with meaning isn't a collection of nice colours. It hands each hue one job and keeps it there. One hue is the brand's accent. A few hues are kept for status: success, information, warning, error. Neutrals carry the surfaces and the text. When a hue takes a second job, both jobs get weaker.

The brand colour is the accent. A status colour is a status colour and nothing else: it belongs on status tags, badges and toasts. It is never the hover, focus or generic accent, which is the default a lot of applications fall into, and never [the colour of selected text](?path=/docs/design-system-principles-interaction--docs#selected-text-is-a-role-not-a-browser-default).

## Seeing lightness evenly

How light a colour looks depends on its hue. A yellow and a blue with the same "lightness" in HSL look nothing alike: the yellow glows and the blue goes nearly black. That's because HSL describes how a screen mixes its red, green and blue, not how your eye sees the result.

<Illustration caption="Squint and only lightness is left: hues set in HSL break into light and dark stripes, the same hues set in OKLCH into one even grey.">
	<PerceptualDrawing />
</Illustration>

A perceptual colour space like **OKLCH** is built the other way round, from how people see. Its lightness is perceived lightness, so two colours at the same lightness look equally light whatever their hue, and the steps of a ramp look evenly spaced. Its chroma and hue are the same dials described above, which makes it the natural space to design a palette in.

## Mixing colours

Mixing two colours means walking a path from one to the other, and the colour space decides which path. **OKLab** walks a straight line: the hue never takes a detour, though the middle can come out a little greyer. **OKLCH** walks round the hue circle, keeping the colour vivid on the way, which is lovely for a gradient between two hues.

That circle is also its catch. White, black and greys have no real hue, so the path's direction depends on whatever tiny hue a neutral happens to carry. Mix a green tint into white and it stays green by luck. Mix it into a dark grey that leans slightly blue and the result can swing halfway round the circle. Pick the space by what should stay put: for a tint mixed into a surface, that's the hue.

## Contrast, held in reserve

The kit's palette is soft and close-toned on purpose. <Pull>Contrast is a signal, not a texture: it belongs to what the user can act on and to what needs their attention, and it is spent sparingly even there.</Pull> Anything passive (a skeleton, a placeholder, a caption, a status dot at rest) sits one quiet step off the surface it is drawn on: enough to be seen at a glance, and never climbing toward the ink.

## Surfaces

A screen is a stack of surfaces: the page itself, the cards that sit on it, the fills inside those cards, and the popups that float above everything. Each level gets a tier of its own, so you can tell at a glance what sits on what. The kit has seven: a page canvas, a dimmest card, the default card, a nested fill, the deepest recess, an overlay for popups and tooltips, and a higher overlay for toasts.

A surface gets **more tinted as you nest** and **lighter as you rise**. In the light theme those pull in opposite directions, which is the thing to get straight: a nested fill is _darker_ than the card it sits in, while a popup floating above that card is not. Write the tier you mean rather than reasoning from "higher number means lighter".

## Surfaces on surfaces

Each tier has an occupant. Reach for one by naming where the thing sits, never by how light you want it to look.

| Tier | What sits there |
| --- | --- |
| Canvas | The page — the routed `<main>`, which takes no fill at all |
| Default card | A sheet on the page |
| Nested fill | A fill within a sheet: an expanded row's sub-table |
| Deepest recess | A well within that |
| Overlay | Off the ladder — popups and tooltips, with toasts on the higher overlay above them |

Read down that column and it is the component tree. Every level is a surface on the one below it, so a component only has to know its own depth.

The page is the canvas, not a surface on it. It declares no fill of its own, so what a sheet is read against is the canvas directly, which makes the canvas the one tier that is a _field_ rather than an object.

The ladder is shorter than the tree, so the rule is not one tier per level — it is **never invent a tier.** A level that would repeat its parent's fill separates by something else: the space around it, its own header band, or a line in [one of the four cases that justify a line](?path=/docs/design-system-principles-separation--docs#the-four-cases-that-justify-a-line).

## Mode and theme

Two settings decide which colours a screen wears, and they are easy to mix up. The **mode** is the user's: light, dark, or auto, which follows the operating system. A **theme** is a complete set of roles a design picks, and the kit ships two, light and dark. Dark mode puts the dark theme on the page. A section of that page, like a band on a home page, can [pick a theme of its own whatever the mode](#a-section-picks-a-theme-with-data-theme-and-the-mode-stays-the-users), and the mode stays the user's.

A section that picks a theme takes the whole set, so everything inside it, from body text to the focus ring, is tuned for that theme. A theme re-points roles and paints nothing, so [the section paints its own background](#a-themed-section-paints-its-own-background) from them. A popup opened from inside floats above the page rather than inside the section, so it opens in the page's theme unless [it is given the section's theme itself](#a-popup-in-a-themed-section-takes-data-theme-itself).

A section can behave in one of three ways as the mode changes:

- **Pinned:** the same theme in both modes, like a dark band that stays dark. Once the mode is dark, the band sits in the same theme as the page around it, and the light and dark alternation that set it apart in light mode is gone.
- **Inverted:** the opposite theme to the page, dark on a light page and light on a dark one. It keeps the alternation in both modes.
- **Bespoke:** a role set of its own, like a band tinted with the brand. It starts from the nearer of the kit's two themes and [re-points the few roles that make it bespoke](#a-bespoke-section-theme-re-points-a-few-roles-on-top-of-data-theme), so every role it leaves alone is still right.

Which of the three a section is, is a design decision, and it has to be made in both modes. Get the dark-mode design before building the page: a section designed in light mode alone leaves the choice to whoever builds it.

<Example kind="do" caption="The dark theme beneath it, and two roles re-pointed to a green tint.">

```scss
.brandBand {
	--sys-color-bg: var(--ref-green-800);
	--sys-color-surface: var(--ref-green-700);

	background-color: var(--sys-color-bg);
}
```

</Example>
<Example kind="dont" caption="Restyled part by part, so every component the list misses keeps the dark theme's surface.">

```scss
.brandBand .card,
.brandBand .field {
	background-color: var(--ref-green-700);
}
```

</Example>
</DoDont>

</Details>

<Details title="A theme re-points the roles and touches nothing else">

A theme re-points layer 2 and touches nothing else. A component that needs to know the active theme is a component that [read a ramp step instead of a role](?path=/docs/design-system-foundation-token-architecture--docs#a-component-reads-a-role-never-a-step).

<DoDont>
<Example kind="do" caption="The component names a role and works in every theme.">

```scss
.card {
	background: var(--sys-color-surface);
}
```

</Example>
<Example kind="dont" caption="A second definition to maintain, and a new theme misses it.">

```scss
.card {
	background: var(--ref-neutral-0);
}

html[data-theme="dark"] .card {
	background: var(--ref-neutral-700);
}
```

</Example>
</DoDont>

</Details>

<Details title="The dark theme is two conditions, kept behind one mixin">

The page's theme is two conditions, not one. A stored mode pins it, and auto follows the operating system — so a dark page is either the attribute on `<html>` or a `prefers-color-scheme` match with no attribute contradicting it. Following the OS is the media query's job, never a script's: a resolved-once attribute freezes on whatever page the user happened to load, and only re-resolves where a component that reads the mode is mounted. The token build writes the dark roles on any `[data-theme="dark"]` element and on the auto-dark `<html>`, so a component that reads roles needs no condition at all. The mixin stays page-level, for a value that follows the page rather than a section, like the scrim behind a dialog or drawer that dims the whole viewport: because the condition is a pair of selectors, it lives behind `theme.dark` so no file spells out half of it.

<DoDont>
<Example kind="do" caption="The mixin carries both halves of the dark condition.">

```scss
.backdrop {
	@include theme.dark {
		--overlay-dim: 0.6;
	}
}
```

</Example>
<Example kind="dont" caption="Pinned dark works, auto never updates.">

```scss
html[data-theme="dark"] .backdrop {
	--overlay-dim: 0.6;
}
```

</Example>
</DoDont>

</Details>

<Details title="Each theme states its color-scheme outright">

A theme declares `color-scheme`. Parts of the page are drawn by the browser, not by this system: scrollbars, form-control internals, spell-check underlines, the canvas behind an overscroll. <Pull>They follow `color-scheme` and nothing else, so a theme that only re-points tokens leaves light scrollbars framing a dark app.</Pull> State the value outright rather than leaving it to `light dark`: the mode has already been resolved by the time the attribute is set, and the browser should not resolve it a second time and disagree.

<DoDont>
<Example
  kind="do"
  caption="Each theme states its colour scheme outright, so the browser's own scrollbar goes dark too."
  visual={
    <div data-theme="dark" className={styles.scroller}>
      <p>Design review · € 120</p>
      <p>Workshop · € 85</p>
      <p>Copywriting · € 32</p>
      <p>Strategy session · € 64</p>
      <p>Consultation · € 48</p>
    </div>
  }>

```css
:root,
[data-theme="light"] {
	color-scheme: light;
}

[data-theme="dark"] {
	color-scheme: dark;
}

@media (prefers-color-scheme: dark) {
	html:not([data-theme="light"]) {
		color-scheme: dark;
	}
}
```

</Example>
<Example
  kind="dont"
  caption="The tokens went dark and the browser's own parts stayed light."
  visual={
    <div
      data-theme="dark"
      className={`${styles.scroller} ${styles.schemeLight}`}>
      <p>Design review · € 120</p>
      <p>Workshop · € 85</p>
      <p>Copywriting · € 32</p>
      <p>Strategy session · € 64</p>
      <p>Consultation · € 48</p>
    </div>
  }>

```css
html[data-theme="dark"] {
	--sys-color-bg: var(--ref-neutral-800);
}
```

</Example>
</DoDont>

</Details>

<Details title="The theme is resolved in the HTML shell, before the first paint">

Resolve the theme before first paint, in the HTML shell. A framework cannot do this: its effects run after the browser has painted, so a dark-mode user gets a white flash on every full page load. The stylesheet is no help either — it is a module the app pulls in, so it lands after the first paint too. That takes two things in the shell: an inline script that pins the stored mode on the root element, and an inline style that states the canvas colour and `color-scheme` for both themes. Set the canvas colour on the root element as well as the body so nothing paints white behind the page.

<DoDont>
<Example kind="do" caption="The shell pins the stored mode before the browser paints anything.">

```html
<script>
	const theme = localStorage.getItem("theme");

	if (theme) document.documentElement.dataset.theme = theme;
</script>
```

</Example>
<Example kind="dont" caption="An effect runs after the first paint, so a dark-mode user sees a white flash on every load.">

```tsx
useEffect(() => {
	document.documentElement.dataset.theme = theme;
}, [theme]);
```

</Example>
</DoDont>

</Details>

<Details title="The shell's raw canvas colour is guarded behind its token">

The shell is the one exception to [colour values living only in the tokens files](?path=/docs/design-system-foundation-token-architecture--docs#a-colour-value-appears-only-in-the-tokens-files): a raw colour may be written there, and only for the canvas. Guard it behind the token so it expires: `var(--sys-color-bg, <raw>)` uses the raw value only while the stylesheet is missing, and every later load of the token wins on its own.

<DoDont>
<Example kind="do" caption="The raw value paints only until the token arrives.">

```css
html {
	background-color: var(--sys-color-bg, #0b0d11);
}
```

</Example>
<Example kind="dont" caption="Unguarded, the raw value is a second canvas colour that has to be kept in step by hand.">

```css
html {
	background-color: #0b0d11;
}
```

</Example>
</DoDont>

</Details>

<Details title="Scrim opacity is the one theme selector a component may hold">

<Beside>

The one legitimate use of a theme selector inside a component file is a value that is not a role and differs per theme, such as scrim opacity:

<Example kind="do" caption="Scrim opacity is not a role, so the component states its dark value itself.">

```scss
.backdrop {
	--overlay-dim: 0.4;

	background-color: rgb(0 0 0 / var(--overlay-dim));

	@include theme.dark {
		--overlay-dim: 0.6;
	}
}
```

</Example>

</Beside>
