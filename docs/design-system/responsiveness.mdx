# Responsiveness

The same product gets read on a phone held in one hand, on a laptop, on a wide monitor, and on a desktop window zoomed to twice its size. It has to work on all of them, and work the same: the screen changes shape, the person and the task don't.

<Illustration caption="Given room, the pieces sprawl into a ragged, organic shape; given a narrow column, the same pieces slot neatly into it. The white one is in both.">
	<ResponsivenessDrawing />
</Illustration>

## Narrow first

The narrow layout is the one to design first. Widening a layout that already works in a small column is a matter of spending the extra room. Narrowing one built for a wide screen means deciding what to give up, and that decision gets made late, under pressure, and it always shows.

A narrow column also asks the useful questions early: what comes first, what belongs together, what the screen is actually for. Once those are settled, a wider screen is a gift rather than a problem.

## Everything, at every width

A narrow screen is not a request for less of the product. Everything a screen offers is still there at every width: it stacks, wraps, or moves into a menu or a sheet, but it is never dropped. Only decoration may go.

<Illustration caption="Wrapped, not dropped: the same six items in one wide row and in a narrow column of pairs, and the one picked out is still there in both.">
	<WrappedDrawing />
</Illustration>

And a narrow screen is not always a phone. Someone with low vision zooms a desktop window in until the text is large enough to read, and the window behaves like a narrow one. That only works if zooming is always allowed, and if the layout changes with the size of the text rather than with a count of device pixels, so a zoomed window gets the narrow layout instead of a wide one that runs off the edge.

## Made for fingers

A pointer is precise and can hover. A fingertip is broad, covers what it touches, and has no hover at all. A screen built only for the pointer fails the finger in two ways.

The first is size. An icon is drawn at the size it reads best, but the control around it has to be big enough to hit. Those are different numbers, and when space gets tight it's the padding, the gaps and the number of items that give way, never the target.

## The edge of the glass

A screen's edge is not a clean line. Phones round their corners, cut a notch into the top and lay a home indicator across the bottom, and a mobile browser grows and shrinks its own toolbars as the page scrolls. A layout that runs right up to the edge ends up under one of them.

So a bar pinned to an edge leaves room for whatever the device has there, which costs nothing on hardware without it. Content keeps one steady distance from the edge, the gutter, and popups keep the same one, so a menu on a phone lines up with the cards beneath it instead of hugging the glass. And a layout that fills the screen's height measures it in a way that survives the toolbars coming and going.

## Room, not screens

A part of a screen rarely knows how wide the screen is, and it shouldn't care. The same component can sit across a whole page, in a side rail or inside a narrow drawer on a wide monitor. What decides its layout is the room it has been given, so it adapts to its own container, at the width where its own content stops fitting. Often it needs no threshold at all: letting things wrap, or a grid that fits as many columns as there is room for, does the job.

<Illustration caption="A responsive component is like a cat: whatever the size of a box, they will make sure they fit. If they fits, they sits, after all.">
	<RoomDrawing />
</Illustration>

Only the things that change with the whole page, like the navigation or a drawer that turns into a sheet, look at the size of the screen. Keeping the two apart matters: a part that answers to both can't be reasoned about, because nobody can tell which one changed it.

## Where an app bends

An app changes its page layout at one screen width. Below it, [the rail becomes a bottom bar](?path=/docs/components-nav--docs#a-bars-entries-are-sized-to-their-longest-word), [a drawer becomes a bottom sheet](?path=/docs/components-drawer--docs#a-drawer-swiped-down-is-a-bottom-sheet) and the gutter narrows. Above it, the wide layout and the wide gutter take over. That one width is set in text-relative units, so zooming in moves a window across it just as a smaller screen would.

That width and both gutters belong to the app, not to the kit. They are page layout, and a media query cannot read a custom property, so the kit's tokens hold neither. No kit component asks about the screen: where one would change with it, the app tells it, through a prop like the drawer's swipe direction or a knob like a popup's distance from the edge.

Because there is only one width, the app's stylesheets and scripts that ask about the screen all read the same value, and none of them holds a number of its own. Two places that each hold the number will hold two different numbers after the next change.

<Details title="Content and popups keep one gutter from the screen's edge">

<Details title="The layout changes at one viewport width, which the app declares">

The page changes layout at one width, and that width is the app's, not the kit's: the kit has no breakpoint token. The app declares it once, as a Sass variable and a script constant, because a custom property cannot be read inside a media query. Every media query on the viewport reads it, in a stylesheet and in script alike, and never a number of its own. A kit component never queries the viewport; the app tells it what changed, through a prop or a knob. Explained in [Where an app bends](#where-an-app-bends).
